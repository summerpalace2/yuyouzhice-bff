# 旅行偏好、行程上下文与记忆摘要架构

## 目标

同一账号可以有多次、不同同行人和不同目的的旅行。系统必须避免把某次行程的临时条件（例如“带父母”“少走路”）错误带到另一份情侣、亲子或朋友出游的行程中；同时又能让用户主动保留稳定、长期的旅行偏好。

本系统把“会话记忆”拆成四个明确的数据域，而不是把所有内容塞进一个用户画像。

| 数据域 | 标识 | 生命周期 | 可影响范围 | 写入规则 |
| --- | --- | --- | --- | --- |
| 游客聊天 | `guest-chat-*` 浏览器本地 ID | 浏览器本地存储 | 仅该游客聊天 | 不写入账号、偏好、行程 |
| 行程工作区 | `plannerSessionId` / `savedTripId` | 草稿到保存行程 | 仅当前行程和对应 AI 对话 | 当前行程约束与局部微调产生快照 |
| 账户正式偏好 | `user_preferences.user_id` | 长期 | 新建规划时可选择沿用 | 用户手动确认或在偏好页编辑；有修订号和审计 |
| 记忆摘要 | `user_memory_summary.user_id`（待实施） | 长期、低频更新 | 仅作为“可选参考” | 由有证据的候选生成，必须可编辑、可撤销 |

## 已落实的隔离规则

1. 游客聊天使用 `guest-chat-*` 浏览器随机 ID；不登录也可以走普通旅行问答。它不具备规划、保存、偏好写入权限。
2. 每次规划已使用 `savedTripId` 或 `plannerSessionId` 生成独立聊天键。打开另一份行程时不会复用其浏览器聊天记录。
3. 规划聊天的偏好上下文由 BFF 从该 `plannerSessionId` 的受权会话恢复，传入当前行程的 `companions`、步行强度、兴趣、交通、餐饮、住宿区域等紧凑快照。
4. 规划聊天不再读取或写入 Redis 的用户全局自动槽位。因此旧聊天里出现过的“老人同行”不能覆盖当前行程明确的“情侣双人”。
5. 普通聊天仍可使用短期会话上下文；它不是长期偏好的权威来源。

### 当前优先级

同一轮请求中，模型和规则必须遵循下面的优先级：

`用户本轮明确要求` > `当前行程约束与已确认局部调整` > `当前行程摘要` > `用户确认的长期偏好` > `记忆摘要（仅建议）` > `普通聊天短期槽位`。

任何低优先级信息与高优先级信息冲突时，必须忽略低优先级信息，并且不得提示用户“不能改”。例如把三峡博物馆换成大足石刻时，应提供时间/距离影响和“仍按这个方案”选项，而不是用旧偏好否决用户选择。

## 记忆摘要第一期设计

### 用户可见内容

旅行档案页新增“旅行记忆摘要”卡片：

- 一段用户可编辑的摘要；
- 最后更新时间与来源数量；
- 已确认事实和“待确认候选”分组；
- 编辑、删除、确认、忽略候选操作；
- 说明“它只影响以后新建规划；当前行程以行程条件为准”。

用户可以直接写入，例如“常与伴侣短途旅行，偏好室内、人文、夜景，尽量少走台阶；不吃香菜”。直接编辑视为显式确认。

### 数据模型（待实施）

建议新增两张表，和 `user_preferences` 并列，不能塞进 `legacy_metadata_json`：

```text
user_memory_summary
- user_id (PK)
- revision
- summary_text
- confirmed_facts_json
- pending_candidates_json
- evidence_count
- updated_at
- created_at

user_memory_evidence
- event_id (PK)
- user_id
- scope_type: PLAN | CHAT | PROFILE_EDIT
- scope_id
- fact_key / fact_value
- evidence_type: EXPLICIT | REPEATED | PLAN_SELECTION
- confidence
- occurred_at
- superseded_at
```

所有写入都应采用和 `user_preferences` 相同的乐观锁和审计原则。聊天原文不应复制进摘要表；证据只保存经过结构化提取、最小必要的信息。

### 候选生成与更新阈值

| 情况 | 处理 |
| --- | --- |
| 用户在偏好页手动编辑，或明确说“请记住” | 立即写入正式偏好/已确认记忆，并记录来源 |
| 两个独立规划都选择相同偏好，或不同会话中重复明确表达 | 生成“待确认候选”，不自动改变画像 |
| 单次行程临时限制（下雨、带长辈、当日时间紧） | 仅保存到行程工作区，不生成长期记忆 |
| 寒暄、简单问答、一次性景点咨询 | 不采集 |
| 新证据与已确认记忆冲突 | 保持原内容，展示“需要确认”的候选 |

摘要生成要有冷却时间：至少累积 2 条独立、合格证据，且距上次摘要更新至少 24 小时；明确编辑不受该冷却限制。模型只能生成候选文案，不能绕过确认直接写入长期记忆。

## 接口与前端分工（待实施）

Java Core 负责账户身份、正式偏好、记忆摘要和审计的唯一权威数据；Node BFF 只做代理、组装经过授权的当前行程快照，不能把任意浏览器参数当作长期偏好；浏览器只保存本地 UI 草稿和游客会话键。

建议接口：

```text
GET   /ai/memory-summary
PATCH /ai/memory-summary                 # 用户直接编辑摘要/事实
GET   /ai/memory-summary/candidates
POST  /ai/memory-summary/candidates/{id}/confirm
POST  /ai/memory-summary/candidates/{id}/dismiss
```

现有 `/ai/preferences` 保持为强类型、可用于规划的正式字段接口。记忆摘要不直接映射为行程约束；创建新规划时由用户选择“沿用长期偏好”，系统再将确认的字段转换为 `AppliedPreferencesSnapshot`。

## 验收标准

1. 同账号先完成“带父母、少走路”的行程，再完成“情侣、夜景”为主的行程；后者聊天不会出现老人或无障碍建议，除非用户本轮明确提出。
2. 两份已保存行程分别打开后，各自只显示自己的聊天记录和行程偏好快照。
3. 游客刷新页面后可续聊同一游客会话；不会被要求登录，也不能发起规划保存。
4. 在档案页确认长期偏好后，新规划可选择沿用；当前已打开行程不会被悄悄重写。
5. 任一次普通聊天、单次景点替换或天气临时要求都不会自动修改长期记忆摘要。
